# SDD 第20段階：Construct 基本表現能力の棚卸し

## 1. 目的と変更境界

第19段階時点の henkan の **Model / PythonFrontend / Realization** の対応範囲を混同せず、次に追加すべき基本表現能力の候補を整理する。これは既存設計の再審査ではなく、**今後実装する新機能の選定資料**である。

- 既存 Construct の意味論は改訂しない。特に `With` と特殊メソッドをめぐる既存判断は対象外。
- Python の全 AST を実装することは目標にしない。表層から要求される効果、必要な契約、背後の言語機構への依存を **新機能ごと**に判断する。
- Realization が未登録であることと、Model が構造を表現できないことは別の事実である。
- 以下の「未対応」は、第19段階コードおよび第20段階の限定的な受理・拒否プローブで確認した範囲を指す。あらゆる入力の網羅的な保証ではない。
- 第20段階では**新規 Construct も Realization も追加しない**。既存 API・意味・受理範囲も変更しない。

確認対象：`src/henkan/constructs.py`、`src/henkan/frontend.py`、`devdocs/canonical_sources/specification/{construct,frontend,composition}.py`、`devdocs/canonical_sources/status/canonical.py`、既存テスト群、および `tests/test_construct_capability_audit_phase20.py`。

## 2. 基本構造の現況

| 領域 | 現在の Model / Frontend で保持する情報 | 今回の調査で区別すべき制限 |
|---|---|---|
| スカラー・式 | 整数・文字列 `Literal`、型付き値参照、整数算術、整数比較、Boolean 演算と否定 | `True` / `False`、`None` の一般値、浮動小数点、除算 `/`、文字列比較、比較チェーン、条件式などは未対応 |
| 束縛・文 | 明示型による `Initialize`、既存名 `Assign`、構造化された式文 | `AugAssign`、分配代入、`pass`、`assert`、分岐内部の新規型付き変数宣言は未対応 |
| 制御フロー | `Branch`、`While`、`For`、`Break`、`Continue`、`With`、`Try` / `Raise` | `match`、式位置の条件選択、例外オブジェクトの一般的操作などは未対応。`With` の既存判断を再検討しない |
| 関数とスコープ | `FunctionDefinition`、レキシカル参照、第一級関数値、間接呼出、戻り値、捕捉関係の静的導出 | キーワード引数、デフォルト引数、`lambda`、`nonlocal`、制御ブロック中の `def` などは未対応。実行時クロージャーの具現化は Realization の領域 |
| 複合値 | 固定長・位置型付きタプル、同種リスト、型付き辞書、要素参照・更新 | タプルの動的添字、アンパック、スライス、リスト長変更メソッド、一般 `len`、内包表記は未対応 |
| クラス | 公称インスタンス型、Receiver、静的単一継承、明示的な `super()`、仮想ディスパッチ | 多重継承、descriptor、メタクラス、動的属性、クラスを値として扱う機構は未対応。第17〜19段階の既存契約を維持 |
| Interface / Port | 既存の明示登録型の Port 参照・呼出 | Python 組込み関数や未知の属性操作を一律に受け入れるわけではない |
| Realization | C/Python の既存 Target Pack と一部の旧来 Constructs への対応 | 算術以降の多くの新しい Model の Target 規則は未登録。Model の「受理」とコード生成・実行の「成立」を同一視しない |

*補足：`ValueKind.BOOLEAN` と `ValueKind.NONE` が存在することは、必ずしも Python の `True` / `False` / `None` 定数を式の値として受理することを意味しない。Boolean 値は比較式などから得られる。`return None` は戻り値が `None` の関数に対する特別な受理ケースとして存在する。*

## 3. 実行可能な証拠

テスト `tests/test_construct_capability_audit_phase20.py` は、新しい意味規則を定めるものではなく、第19段階の動作を観測する回帰用プローブである。

### 3.1 既存能力の維持を確認

- `1 + 2 * 3`、`(1 < 2) and (3 < 4)` は型付き式 Construct になる。
- `if`、`for`、`with`、限定された `try` はそれぞれの Construct を保持する。
- 型付き関数と `Return`、タプル・リスト・辞書生成、静的クラス定義を保持する。
- 関数値呼出 `FunctionValueCall` とインスタンスの仮想呼出 `MethodCall(VIRTUAL)` を区別する。

### 3.2 Frontend が明示的に拒否する例

| 入力例 | 観測される境界 | 分類 |
|---|---|---|
| `flag: bool = True` | `ast.Constant` の Boolean 値を受理しない | スカラー値の欠落候補 |
| `x: object = None` | `None` の一般値式を受理しない | スカラー値の欠落候補 |
| `n: float = 1.25` | `float` の型注釈を受理しない | 型体系・演算の候補 |
| `9 / 3`、`2 ** 3`、`1 << 2` | 対象演算子を拒否 | 演算規則の選択が必要 |
| `1 if 1 < 2 else 3` | `ast.IfExp` を拒否 | 式としての分岐候補 |
| `1 < 2 < 3` | 比較チェーンを拒否 | 評価順・一回評価の検討対象 |
| `'a' == 'b'` | 整数以外の比較を拒否 | 型別演算の候補 |
| `n += 2` | `ast.AugAssign` を拒否 | 単純な `Assign` への無条件展開は保留 |
| `pass`、`assert ...`、`match ...` | 該当文を拒否 | それぞれ独立評価が必要 |
| `lambda`、リスト/辞書内包表記 | 該当式を拒否 | 既存関数・ループへの正規化可否を検討 |
| `len(xs)`、`xs.append(2)` | 組込み・メソッドを未登録操作として拒否 | 複合値の操作契約候補 |
| `f(n=1)` | 関数呼出のキーワード引数を拒否 | 引数束縛規則の候補 |
| `a, b = pair` | 分配代入を拒否 | 変数宣言・代入の候補 |
| `t[i]`（タプル） | 静的非負整数以外の位置を拒否 | 既存タプル契約を維持 |
| `if ...: new: int = ...` | 分岐内の新規束縛を拒否 | 既存スコープ契約を維持 |

この一覧は **Python 全 AST ノードを分類した表ではない**。特に表にない構文を暗黙の対応扱いにしない。

## 4. 次の新機能を選ぶための判定手順

新しい構文を要求されたとき、次の順序で判断する。

1. **表層の効果**：どの値、制御、束縛、参照関係を表現したいのかを具体的なコードで示す。
2. **背後への依存**：その効果に Python の特殊メソッド、動的な関数・クラス変換、実行時属性探索などが不可欠かを判断する。「裏側だから不可」と一律判定しない。
3. **採用する意味**：元の Python の意味をそのまま採用するか、限定するかを **新機能についてのみ** 明示する。限定して受け入れる場合には、元の Python と一致しない点を必ず記録する。
4. **既存 Model による表現**：新しい Construct が本当に必要か検討する。ただし、意味の異なるものを無理に統合しない。
5. **実現境界**：Realization が要求する契約を渡せるか検証し、非対応ならその Realization が拒否する。Model の契約を Target 都合で変更しない。

## 5. 今後の優先候補（採用決定ではない）

| 優先 | 候補 | 根拠・設計上の留意点 | 次の作業 |
|---|---|---|---|
| **P1** | Boolean 定数値 | `ValueKind.BOOLEAN` と Boolean 演算はすでに存在するが、`True`/`False` を直接記述できない。基本値の明白な穴 | 既存 `Literal` の int/str 契約を無断拡張せず、専用値表現か明示契約拡張かを新機能として決める |
| **P1** | `None` を一般値として扱う範囲 | `None` 戻り値契約と一般の `None` 式が分かれている。クラスや関数の API 表現に影響 | 「単一 `None` 値」「Optional/Union」などを混同せず、必要な最小契約を分離する |
| **P1/P2** | 式としての条件選択 | `Branch` は文で、`x if c else y` は一つの値を生む式。既存 Branch の置換だけでは一般に足りない | 型一致・評価順・片側だけの評価を決め、必要なら新しい `Value` を検討する |
| **P2** | 複合値の基本操作 (`len` 等) | リスト・辞書は存在するが、長さや基本操作に接続できない | 静的な型が保証する操作だけを採用できるか評価。Python の任意の `__len__` を暗黙採用しない |
| **P2** | スカラー演算型の拡張 | 浮動小数点、文字列比較、通常の `/`、演算種別を追加する要求が想定される | 丸め・例外・文字列照合の意味を個別に決定する |
| **P2/P3** | 宣言・代入・引数束縛の表現 | キーワード引数、分配代入、制御内部の宣言、`AugAssign` は現在制限されている | 評価順・束縛・再代入の既存契約を守り、新規機能として必要性を確認する |
| **P3** | 省略構文 (`pass`、内包表記など) | 基本構造の組合せで表せる可能性がある | 評価順・一回評価を保持できる場合だけ Frontend 正規化を検討 |
| **保留** | デコレーター、descriptor、メタクラス、MRO 一般化など | 表層の効果と複雑な Python 内部機構が強く関係 | 具体的な利用要求が出たときに意味の限定を個別判断する |

**P1 は必ず実装するという意味ではない。** 既存の契約を維持しながら設計検討へ進む優先順位である。新機能の追加前に、肯定例・拒否例・Target の非対応境界を仕様とテストで確定する。

## 6. 提案する次の区間

- **第21段階（提案）**：Boolean 定数値を最小の新機能として仕様化・実装するかを判断し、実装する場合は型付き値・Frontend・拒否テストを付ける。既存の `Literal` 契約を変更するかは自動決定しない。
- **次の段階**：`None` と条件選択式をそれぞれ別の意思決定として検討する。例外・クロージャー・クラスの既存設計は触らない。
- **並行する未着手事項**：新しい Construct に対する各 Target Realization、Interface/CLI などは別作業区間として管理する。この監査を「コード生成済み」の根拠にしない。
