# pyinto Development Status

Implementation facts and outstanding items for the development-stage project.

## Development stage

Version `0.3.0`, Alpha. The foundational migration to the Template / Slot model has been implemented. Backward compatibility is not guaranteed.

## Current distribution and development structure (0.3.0)

- **Host (`pyinto`):** Foundation, Language Interface, Python Source Adapter, and Surface are provided in one package. `convert()` and `realize()` require explicit Realization registration and never implicitly select a particular Target.
- **Artifact submission:** A Target Pack declares `composition` or `structural` through `dispatch` and creates a fresh `session` state for each generation request. The Host controls Realization invocation; the final artifact is obtained through Session `finish()` and returned without conversion. `composition` retains Template/Slot chaining, with `TextArtifactSession` supporting existing string generation. `structural` visits all Constructs in depth-first preorder following `parts()` order; `visit` implementations operate on Target state. Non-textual results, such as `dict` and `bytes`, are possible. `semantics` distinguishes meaning preservation (default) from projection, where execution-semantic `supports` matching is not required. `unhandled` declares either `error` (default) or `traverse`; the latter is available only to Structural Projection Targets. Unhandled Realizations are skipped while traversal continues into children, but Models unregistered with Admission are always rejected. At registration, known finite variant candidates are checked using the Construct's `variant_domain()`; nonexistent variants are rejected. Omission still means `default` and is disallowed for Constructs with multiple variants or an open domain in Structural Projection Targets. `variant = "*"` explicitly matches any variant, with exact matches taking precedence. Open domains, such as dynamic `IntrinsicCall` variants, are not exhaustively enumerated. Comprehensive correctness contracts for individual projections and automatic embedding of semantic-mode information into artifacts have not been implemented.
- **Optional runtime information:** The top-level `__pyinto_runtime__()` hook is excluded from the static Construct Model. A Target Pack declares its `purpose`: `conversion` (default) rejects `__pyinto_runtime__`, `inspection` accepts and reads it without executing, and `execution` declares its use with `runtime` (`required` / `optional`). A Source that defines `__pyinto_runtime__` cannot import `pyinto.kinds`. After static checks and dispatch, the Host can execute trusted Python and pass the hook result to `Session.finish(R)`. With `optional`, `RUNTIME_ABSENT` distinguishes a missing hook from a returned `None`; model-only `realize()` cannot satisfy `required`. The Host does not interpret runtime values. A Target can additionally declare `runtime_schema` as an ordinary class (`isinstance` shorthand) or a predicate over the result (including its values). The Host validates R before `finish(R)`, skips validation for an absent optional hook, and does not implement a generic-type parser.
- **Declaration form:** Target Pack, realization entry, and Interface Mapping declarations are written with role markers (`@realizes` / `@naming` / `@maps` / `@signature`) and plain class attributes using `=`. Only the class's own `vars(cls)` is read; unknown public names, wrong value types, and inheritance from declaration classes are rejected at registration. The Host wheel has no runtime dependency on third-party packages.
- **Kinds:** `pyinto.kinds` provides vocabulary that passes type, memory, and declaration information to Targets, split into the surfaces `datatypes` / `memory` / `declarations` and the tiers `general` / `detailed`. `general` is Python's built-in types with `Wide` / `Narrow` / `Unsigned` / `Size` / `Index` / `Byte` and `Owned` / `Shared` / `Buffer` / the `Memory` operations, the general vocabulary every Target interprets. `detailed` holds choices close to particular languages such as `Int[N]`, `Pointer[T]`, `Null`, and `@Interface`. The Host defines no meaning; it records them in the Model as Python-side shapes and `KindLabel` values and passes them to Targets. Labels take no part in type-compatibility decisions, and operations involving kinds require no Python-semantics obligations. Targets register type spellings with the elements of `pyinto.model.kinds` and can check their interpretation and coverage of the general vocabulary with `profile()` and `missing_general()`. The C reference Realizer realizes only some of the words.
- **Mapped-object shape:** Objects of classes registered through a class mapping are created by an argument-free `Class.variant()` call, and `MappedType` holds only its source and variant. Class mappings are verified with a test counter, and function mappings are shown in `examples/mapping_demo`.
- **Development C Realizer:** An unpublished reference implementation moved to `tests/support/c_realizer/`. The import `from tests.support.c_realizer import c_bindings` is only for development and tests; neither a separate wheel nor automatic selection is provided. The published Host does not depend on the C implementation.
- **Development Python Realizer:** Located in `tests/support/python_realizer/` and used only as an unpublished test fixture. It is excluded from the Host wheel and does not guarantee preservation of type annotations or fully reversible conversion.
- **Interface Mapping:** External Python APIs are normalized into Constructs through the existing registration API in `pyinto.interface_mapping`. `pyinto.interfaces` is a thin facade re-exporting existing Language/Builtins Constructs without changing identity. Automatic discovery and registration of external Interfaces, a CLI, Target discovery, and Bundle composition have not been implemented.
- **Model type information:** The type of a mapped object is represented by `MappedType`, `ValueKind.MAPPED_OBJECT`, and the type-spelling key `mapped:`. It is separate from the kind `@Interface`.
- **Distribution scope:** Only the Host wheel is distributed. Both C and Python reference Realizers are maintained under `tests/support/` to test the Host's public API boundary and meaning preservation. Verifying meaning preservation requires execution tests in addition to declared-contract checks.

## Implemented

- **0.3.0, Target purpose:** Added `purpose` (`conversion` / `inspection` / `execution`) to Target Packs and narrowed `runtime` to `required` / `optional`, for `execution` only. `forbidden` was replaced by `conversion` (the default), and `ignored` by the reading purpose `inspection` (which requires `semantics = "projection"`) (CVT_005 to CVT_007). Importing `pyinto.kinds` in a Source that defines `__pyinto_runtime__` is rejected (FRT_081).
- **0.2.0, kind vocabulary:** Added `pyinto.kinds`, recording type, memory, and declaration words in the Model as labels without meaning, split into surfaces and the `general` / `detailed` tiers (CST_076 to CST_081, FRT_075 to FRT_078, FRT_080). Targets register type spellings with the elements of `pyinto.model.kinds` and can use `profile()` / `missing_general()` / `requires` on type spellings. Operations involving kinds require no Python-semantics obligations (CMP_033 to CMP_036). Mapped-object constructor arguments (integer constraints) and the memory class-mapping demo were removed at the same time (FRT_079).
- **0.2.0, terminology:** The conversion flow is now named with one set of words: Source → Host → Model → Realizer → Artifact. Target Implementation became Realizer; each rule inside a Realizer is a Realization and its entry declaration is the Target Pack. Model means the tree of Constructs built from one Source. The Realizer documents moved to `realizer/` (`docs/realizer/` in English). In Interface Mapping, the Port names that remained in the Model were renamed to `MappedType`, `ValueKind.MAPPED_OBJECT`, `Symbol.mapped_type`, and the type-spelling key `mapped:`; the documents call them function mappings, class mappings, and mapped objects (CST_002, FRT_079). The development contract boundaries were renamed `FrontendBoundary` / `CompositionBoundary`, and the demo moved to `examples/mapping_demo`.
- **0.2.0, declarations as plain class attributes:** The `@=` descriptions of Target Packs, realization entries, and Interface Mappings were replaced by ordinary `=`, and the `pack_` prefix was removed from Pack declaration names. `requires` is given as a tuple of `str`. Reading and validating declarations (rejecting unknown names, wrong types, inheritance, and repeated markers; CMP_032) is implemented within the Host, and the runtime dependency `shikumi` was removed. Role markers, the meaning of each declaration, and the Admission, Dispatch, and Runtime contracts are unchanged.
- **Iteration 46, typed variadic arguments for self-defined functions:** Top-level `def f(*items: T)` and the same form with fixed parameters are represented through `FunctionSignature.variadic_parameter` and type information for a runtime homogeneous variadic `TupleType`. Zero or more statically explicit positional arguments remain ordered in the existing `FunctionCall`, and `len`, `sum`, and `for` can operate on them inside the function. This is distinguished from a fixed-length Tuple; assignment from a compatible fixed-length Tuple value to the homogeneous variadic Tuple type is accepted. Definitions and calls separately require Admission obligations `function.variadic.tuple_binding` and `call.variadic.tuple_binding`. Dynamic `*` expansion, treating these functions as function values, variadic methods or nested functions, and `**kwargs` remain unsupported. No C Target Realization was added.
- **Iteration 45, scalar augmented assignment with `global`:** The explicit globals introduced in Iteration 44 now support existing `int`/`float` `AugAssign` in addition to simple assignment. Original Symbol identity, evaluation order, and rebinding contracts are preserved. Local-name precollection now includes `AugAssign`, preventing an unqualified `counter += 1` from resolving incorrectly to an outer Symbol of the same name. Model and Target rules were unchanged; an unsupported C Target rejects the operation.
- **Iteration 44, restricted `global`:** In a typed top-level function, leading `global` statements following the docstring may name only typed module variables initialized before the function definition. Reads and simple reassignment normalize to `Reference` / `Assign` pointing to the original `Symbol(scope=())`. Forward, unknown, and Port names; parameter collisions; typed redeclarations; nested functions and methods; `global` appearing later or inside control-flow bodies; and iteration targets are rejected. No `global` Construct or C function Realization was added.
- **Iteration 43, recursive type spelling:** The callable form `type_name @= callable` receives `(shape, spell)`. `spell(inner_type)` reuses rules registered with the current Target, supporting nested list, dict, tuple, Callable, and references from Port types. Unregistered nested types, invalid type names, and recursion involving the same concrete type are explicitly rejected. State does not leak between independent requests. Fixed type names remain supported; there is no compatibility call for legacy one-argument selectors.
- **Iteration 42, type Slots and layout:** A type-spelling selector receives the complete composite `ValueType` shape; Port types remain `PortType`. The function result type is exposed as `${return_type}` on `FunctionDefinition`, rendered along the same Composer route as existing type Slots such as `FieldDefinition`. Model-originated tuple type Slots may specify separators, e.g. `separators @= {"parameters": ", "}`. Unsupported types, invalid Slots, and invalid separators are explicitly rejected.
- **Shikumi parent/child declarations for external function Interface Mapping:** Declare `@maps(function)` on a parent class, `@signature(...)` on nested classes, and `factory @= ...` in the children; `InterfaceMappingRegistry.from_declarations()` converts them into existing function Mappings. The defining origin of function objects is used; dynamic calls and automatic registration are not performed. Existing signature matching and Frontend acceptance/rejection boundaries are preserved. Class/method Mapping is not covered; re-exports for which defining origin and public name differ need separate design.
- **Static variadic positional parameters and overloads for external Interface function Mapping:** `InterfaceVariadicParameter` supplies any number of explicitly given positional arguments to the Model factory in order. Multiple distinct signatures may be registered for the same fully qualified name. Each argument expression is normalized exactly once regardless of candidate count, and only a uniquely matching signature is chosen. Duplicate registrations, ambiguous calls, absent matches, dynamic expansions, and reordered arguments that cannot preserve meaning are rejected. Registration order is never used to infer signature priority. No additional Target implementation was introduced.
- **Argument normalization for external Interface function Mapping:** `InterfaceParameter` declares static named parameters, types, and immutable literal defaults. Positional, keyword, and mixed calls are bound to the same declaration order. Unknown or duplicated names, missing arguments, type mismatches, and expanded arguments are rejected. Reordering that would change side-effect evaluation order is explicitly unsupported. External Class and Method Mappings and Target Realizations were unchanged.
- **Absolute-import extensions in the Python Source Adapter:** `import module`, `as` aliases, multi-level modules, and `from package import submodule` are connected statically to existing Interface Mapping. There is no standard-library versus third-party distinction; unregistered names and collisions are rejected. Imports do not load modules. Model and Target Realizations were unchanged. Relative, dynamic, and in-scope imports remain unsupported.
- **Public surface redesign, step 5:** Host Shikumi declarations are limited to `@realizes(element)` and `@naming`. C Target, development Python Realizer, tests, and examples use this single declaration system. There are no compatibility information types, assignment descriptors, registration branches, or assignment processing for naming markers. Missing declarations and duplicate subjects are rejected. General external direct-Call elements and modeling `accepts` as a typed element remain unimplemented.
- **Public surface redesign, step 4:** Migrated all 22 C Target declarations and all 26 unpublished development Python Realizer declarations to `@realizes(element)` / `@naming`. Construct variants, direct `print` calls, primitive type spellings, naming policies, and contract support/rejection behavior were preserved.
- **Public surface redesign, step 3:** Added argument-free marker `@naming`. It cannot share a declaration class with `@realizes(element)`. Duplicate naming policies within a Target, invalid `requirement_line` Slots, and erroneous `supports` on Naming are rejected.
- **Public surface redesign, step 2:** Added Shikumi `@realizes(element)` to connect Construct classes such as `lang.While`, `builtin.PrintCall` (direct Call previously keyed `print`), ValueKinds such as `vt.Integer`, and PortType instances to the appropriate existing Registry registration paths. `builtin.PrintValues` remains a separate Construct. Duplicate registrations, invalid elements, missing contract support, and invalid Slots are explicitly rejected. C and development Python Realizers were migrated in step 4. Frontend conversion scope was unchanged.
- **Public surface cleanup, step 1:** Added `pyinto.interfaces.language`, `pyinto.interfaces.builtins`, and `pyinto.model.value_types` as public Model facades. These re-export existing Constructs and ValueKinds; type identity, Admission, and Realization selection are unchanged.
- **Iteration 36 migration step 8:** Verified separate wheels for the two distributions, clean installs, no reverse import from Host to C, explicitly chosen Realizations in the public API, C generation/compilation/execution via gcc, and explicit refusal of unsupported Constructs. Development Contrace contracts remain in source but are excluded from the Host wheel. Regression checks were added without changing Model semantics, Frontend acceptance, or Realization coverage. Logical separation completed one cycle, but the Git repository had not yet been physically split.

It is excluded from the Host wheel, never implicitly used by the Surface, and explicitly selected only for existing Model-to-Python generation and execution regression tests. Construct, Admission, and Realization scope was unchanged. This does not guarantee type-annotation-preserving round trips; that remains a verification task.

- **Model capability expansion 12 (Iteration 35):** Only in control-flow bodies (`if`/`else`, `while`/`else`, `for`/`else`, and `with`), typed initialized declarations normalize to existing `Initialize` (FRT_071). Names declared there are accessible only in subsequent statements of that body and nested bodies, not outside its branch or in a separate clause. No Python block scope is introduced; Symbols still belong to the containing function/module. Lambda captures of newly introduced bindings, Port declaration/rebinding, and new declarations immediately within `try` remain rejected. This concluded the syntax expansion without extending existing Construct or Target Pack realization scope. Subsequent work emphasized Python Pack Realization and meaning-preservation testing, with focused C Pack checks as needed.
- **Model capability expansion 11 (Iteration 34):** `IterationEntry.introduces_binding` distinguishes one newly introduced iteration variable in `for`. Its type is established only from `range`, `str`, typed Lists, and nonempty homogeneous Tuples, without inventing an initializer for empty iteration. References to introduced names are restricted to the body; use in `else` or subsequent statements is rejected without analysis. Introduced bindings require `iteration.binding.introduced` Admission; standard Python/C Packs remain unsupported.
- **Model capability expansion 10 (Iteration 33):** `SliceValue` preserves slices of typed Lists and Strings (CST_072 / FRT_069). Omitted versus explicit start/stop/step values are distinguished. Evaluation-once and target-before-bounds order, Python negative indexes, bound adjustment, zero-step exceptions, shallow outer List copies, and Unicode units for Strings are recorded as contracts. Dict/Tuple slices and slice assignment are rejected; standard Python/C Packs did not gain implementations.
- **Model capability expansion 9 (Iteration 32):** `Membership` now represents membership of elements in `list[T]` and keys in `dict[K,V]`. Left-to-right evaluation, Python membership rules for each category, and negation are separate contracts; `StringContains` remains (CST_071 / FRT_068). Known types are checked. Dynamic containment protocols, Tuple membership, and membership in comparison chains are rejected. No Python/C Pack recipes were added.
- **Model capability expansion 8 (Iteration 31):** Added `UnpackAssign` for reassignment of already-declared names from fixed-length Tuples (CST_070 / FRT_067). The right-hand side is evaluated once, all positions are resolved, and targets are updated left to right. Nested/starred targets, new declarations, and Port rebinding are unsupported. No Python/C Pack Realization was added.
- **Model capability expansion 7 (Iteration 30):** `FormattedString` preserves segments of f-strings without format specifications and their evaluation order. - **Model capability expansion 6 (Iteration 29):** Registered fifteen zero-argument or single-argument conversion signatures for `str`/`int`/`float` and typed `int`/`float`/`str`/`bool`, plus `str.upper`/`str.lower`, in the standard provider table `standard_intrinsics()` (CST_068 / FRT_065). The default PythonFrontend uses this table, which may be overridden with explicit `intrinsics`. Per-conversion contracts and static type/arity rejection are verified. - **Model capability expansion 5 (Iteration 28):** `IntrinsicRegistry` accepts multiple static signatures for one operation family. `IntrinsicTypeVar` and `IntrinsicListType` apply only inside Intrinsic signatures, resolving such cases as `list[T].append(T)` and `str(int)` versus `str(float)` unambiguously from known types (CST_067 / FRT_064). Duplicate signatures, multiple matching candidates, type mismatches, and unbound return type variables are rejected. Concrete selected signatures and signature-specific obligations are retained in the Model; Realization matches `supports` within the same family. None-valued primitive-method expression statements are supported. General inference, implicit conversion, and Python/C Pack implementation were not added.
- **Model capability expansion 4 (Iteration 27):** Introduced provider-defined `IntrinsicDefinition`, `IntrinsicRegistry`, and `IntrinsicCall` (CST_066 / FRT_063). Receiver presence, recursively typed arguments/result, operation keys, and extra semantic obligations are represented independently of Target and Frontend. Construct-provider Admission requires once-only ordered evaluation of receiver and arguments, rejecting omitted, duplicated, or reordered Slots in simple string Templates. The default registry was empty at this stage; tests normalized only explicitly registered typed operations. Existing builtins and standard Python/C Pack scopes were unchanged. Dynamic method resolution, inference, overloads, and Target Realization were not supported at this stage.

- **Iteration 23:** Added typed binary operand evaluation order, Port Call explicit-argument order, and function-value callee-first semantics to Construct-provider Admission (CMP_020). - **Typed-variable declaration requirement:** The Frontend rejects new bindings without type annotations and type mismatches; reassignment uses the existing explicit type.
- **AST normalization:** Python AST normalizes into `Program`, `Block`, `Branch`, `While`, `For`, `With`, `Break`, `Continue`, `Range`, `IterationEntry`, `ContextEntry`, `Reference`, `Literal`, `Initialize`, `Assign`, `AugAssign`, `Comparison`, `ComparisonChain`, `Call`, `ExpressionStatement`, `Arithmetic`, `IntegerUnary`, `BooleanOperation`, `BooleanNot`, `BooleanLiteral`, `NoneLiteral`, `ConditionalExpression`, `Length`, `Absolute`, `Extremum`, `IntegerSum`, `BooleanAggregate`, `FunctionDefinition`, `FunctionCall`, `FunctionValueCall`, `LambdaValue`, `Return`, `Parameter`, `FunctionSignature`, `TupleValue`, `TupleElement`, `Raise`, `ExceptHandler`, and `Try`.
- **Construct APIs:** Removed `emit()` and `Snippets` (AAA+Cleanup); each Construct provides named children via `parts()` and a structural `variant()`.
- **Target Pack declaration:** Shikumi declarations supply a single `template` or dynamic `render` template choice; extra/missing Holes and duplicate definitions are rejected.
- **Composer and Renderer:** Composer recursively connects Templates and Slots without prematurely stringifying children. Renderer handles indentation of line-based Slots and emits the final string.
- **EmitContext:** During Binding selection, exposes root, current Construct, parent, ancestors, and path. Source Constructs must not be modified; generation state is separate. Children are composed in first-Slot occurrence order, and header/fresh-name state is reset for each request.
- **`while`:** Normalized as condition expression, body Block, and optional `else` Block. C/Python Bindings realize loops and normal-completion blocks. `Break`/`Continue` are independent Constructs; C/Python loop Bindings handle interruption by `break` and normal-completion `else`.
- **`for`:** `IterationEntry` represents iteration binding and a Value represents its source. C Binding handles integer `range`; Python Binding preserves iteration structure. Both have tests for `break`, `continue`, and `else`.
- **`with`:** Normalizes ordered `ContextEntry` elements and a body Block. Python Binding realizes `with`; an unregistered C Binding produces a clear C conversion error rather than rejecting the Construct itself.
- **Header requirements:** Collected while composing children and placed at the final rendering stage.
- **Target substitution:** C Target Pack and Python Target Pack can be substituted.
- **External mappings:** Explicit registration and Target Binding for a function mapping of an external function (`DeviceIsReady`) and a class mapping of a test counter.
- **Mapped-object lifetime:** Class-mapping cleanup (`close()`) is an explicit standalone operation; no automatic Cleanup.
- **Mapped-object aliases and types:** Simple alias declaration `a: Counter = Counter.open(); b: Counter = a` and Target type resolution for mapped types are supported. A type spelling without a matching Binding is rejected.

## Unimplemented features and limitations

- Iteration 16 Slot verification covers only string Templates. Targets using dynamic `TemplatePlan` require individual execution tests for actual meaning preservation; no mechanical proof for arbitrary Realizations is provided.
- Iteration 15 added admission matching for five direct-call forms, but enforcement of **all** audited non-field semantic obligations remains **unimplemented**. Iteration, short circuiting, closure lifetime, `finally`, and correctness of Target Realizations still need verification. `supports` checks depend on a Realization's own claims and cannot by themselves detect a false claim.
- Frontend mixins have been removed, but Services still call across domains through delegation entry points on the coordinator. Further cleanup depends on need and complexity. Decorator registration/effect handlers exist, but arbitrary replacement by Constructs/Interfaces other than the currently typed results (`ClassDecorationPlan`, `MethodKind`, and same-signature `FunctionDefinition`) and composition of multiple decorators require separate design. Merely registering a name does not make its behavior available.
- Declarations of new variables inside loops and rebinding of mapped objects.
- General `for` iterables in the C Target, `with` entry/exit and exception suppression, and reproduction in C of Python exception classes (for example, zero `range` step).
- All AST variants of `for` / `with`, including destructuring assignment.
- Target Realizations for newly modeled arithmetic and logical operations in both C and Python.
- Target Realizations for Phase 24 floating-point arithmetic/comparisons and string operations; additional Interfaces specifying float precision, implicit numeric promotions, string slicing, and runtime Unicode indexing representations on the Target are also unimplemented. Because Python `//` / `%` rules and `and` / `or` short circuiting are delegated to the Target, conversion without a supporting Realization explicitly fails.
- Floating point, general `/` / `**` / bitwise operations, truth-value conversion, general truthiness, augmented assignment of mutable objects, and comparison chains involving arbitrary types, identity, or membership.
- General acceptance of all Python builtins (`sum`, `zip`, `enumerate`, etc.), arbitrary-object `__len__` / `__abs__`, `min`/`max` on arbitrary Iterables, `key=` / `default=`, and Target Realizations for new builtin operations.
- General `Optional` / `Union` values and typed collection elements that may contain `None`; Target Realizations for Boolean/None/conditional expressions.
- Runtime indexing (including negative indexes), slicing, element assignment, and unpacking of variadic Tuple types, plus Tuple Target Realizations. Access to fixed Tuples is restricted to static nonnegative integer indexes. Length-changing List methods, slicing, comprehensions, and related Target Realizations are unsupported.
- Arbitrary exception types; exception instances as general values; `except ... as`, bare `except`, re-raise and cause chaining, `except*`, non-string/multiargument exception messages, and Target Realizations for exception Constructs. Missing Realizations cause explicit rejection.
- Equivalent conversion of every Python AST form or Python runtime semantic.
- Multiple possible mapped-object references or rebinding across branches; advanced function parameter forms; unsupported general decorators; Target Realizations for function values; closure capture lifetime after escape; `global` outside the restricted subset; general Python scoping such as `nonlocal`; generalized references via collections. `def` inside a function's control structure is unsupported.
- Complete analysis of return paths and Target Realizations for function definition/call/return. The current Model preserves static structural pathways but does not guarantee that they are realized by a Target.
- Multiple inheritance, general MRO, dynamic base changes, descriptors, metaclasses, class attributes, properties, decorators outside the three selected forms, first-class class objects, dynamic attribute modifications, dynamic keywords/expanded arguments, and general runtime special methods; plus Target Realizations for new class Constructs.
- General C Target representations of `typing.Any` / `object`.
- Arbitrary relocation of Target-specific expression preparation steps to different execution positions.
- Static guarantees against allocation failure, leaks, double frees, or use-after-free.
- End-to-end semantic equivalence between mapped Python libraries and libraries written in other languages.
- External Target Pack distribution, automatic discovery, and a stabilized Target Binding API.
- Public-facing English documentation.

Unsupported features are not inferred and implemented automatically. Expansion requires explicitly specified structures, contracts, and Bindings.
